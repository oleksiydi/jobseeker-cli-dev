# AGENTS.md

## Назначение
Этот файл фиксирует рабочие правила для Codex и разработчиков в проекте `jobseeker-cli`.
Цель: сохранить проект рабочим, читаемым и предсказуемым при развитии ETL/ELT пайплайнов.

## Текущие решения по стеку
- HTTP-клиент: используем `requests` + `Session`.
- `httpx` не добавляем без явной причины (техническая потребность или доказанная выгода).
- Зависимости можно добавлять, но держим их минимальными и обоснованными.

## ВАЖНО: выбор библиотек и фреймворков (приоритетное правило)
- Цель: использовать свободные, зрелые и общепринятые в индустрии решения, не переизобретая инфраструктурные компоненты без необходимости.
- Дополнительная цель: заметно сокращать объем поддерживаемого кода проекта, если это не ухудшает прозрачность и надежность.
- Базовый порядок выбора:
1. Стандартная библиотека Python.
2. Де-факто индустриальный open-source инструмент (активный, стабильный, документированный).
3. Локальная самописная реализация.
- Исключение с повышенным приоритетом:
- если индустриальный open-source инструмент дает функциональность и надежность заметно выше, чем стандартная библиотека Python, ему отдается приоритет.
- если индустриальный open-source инструмент дает сопоставимую функциональность, но существенно уменьшает объем самописного кода и стоимость сопровождения, ему также отдается приоритет.
- Когда добавляем зависимость:
- она решает нетривиальную задачу лучше самописного кода;
- снижает риск ошибок и упрощает сопровождение;
- имеет активную поддержку и понятную лицензию.
- сокращает объем кода, который команде нужно читать, объяснять новичкам и поддерживать.
- Когда пишем локально:
- задача маленькая и стабильная;
- код короткий и прозрачный;
- новая зависимость создаст больше сложности, чем пользы.
- локальная реализация полезна как учебный пример и не превращается в отдельный "мини-фреймворк".
- Для спорных решений фиксируем в PR/коммите:
- выбранный вариант;
- альтернативы;
- краткий компромисс (качество/скорость/поддержка/сложность).

## Конфигурация и флаги
- Стандартная директория конфигов: `conf/`.
- Основной конфиг: `conf/app.json`.
- Профили: `conf/profiles/default.profile.json`.
- Feature flags: задаются в config-файле.
- Override: через ENV-переменные.
- Секреты (ключи, URI, токены): только через ENV (`.env`), не в JSON.
- При добавлении новых ENV/CLI-параметров обязательно:
  - обновить `.env.example` (дефолт и комментарий назначения);
  - обновить документацию (`README.md` и/или `docs/process/*`) с приоритетом переопределений:
    `CLI > ENV > code defaults`;
  - зафиксировать fallback-поведение и дефолтные значения.

## Безопасность секретов
- Секреты не выводим в чат, логи, скриншоты, отчеты и коммиты.
- Запрещено логировать значения `OPENAI_API_KEY`, `MONGODB_URI` и других токенов.
- Для диагностики используем только безопасные проверки вида `bool(os.getenv(...))`.
- При любой утечке секрета ключ считается скомпрометированным и подлежит немедленной ротации.

## MongoDB: неизменяемые имена коллекций
Нельзя переименовывать эти коллекции:
- `stellenangebote`
- `jobdetails`
- `analysen`
- `profiles`

## Правила для пайплайнов
- Идемпотентность обязательна: повторный запуск не должен делать лишние записи.
- Сбор списка/деталей должен минимально трогать документы, если вход не изменился.
- Анализ должен пропускать вакансию, если не изменились `meta + details + profile + prompt + model`.
- Для `analysen` используем версионирование и `input_hash`; новую версию создаем только при изменении входа.
- В основных коллекциях храним только актуальные данные.
- Историю изменений храним в дополнительных коллекциях, а не в массивах внутри основных документов.
- Для истории используем отдельные коллекции по доменам (например: `stellenangebote_history`, `jobdetails_history`, `profiles_history`), с TTL/архивной политикой при необходимости.
- Для `analysen` отдельная `*_history` коллекция не нужна: версии храним прямо в `analysen`.
- Для `jobdetails` обязательно сохраняем фильтр по датам перед API-запросом:
- сравнение `stellenangebote.modifikationsTimestamp` и `jobdetails.aenderungsdatum` как первый уровень защиты от лишних вызовов.
- Это правило обязательно для контроля нагрузки и снижения риска блокировки по частоте запросов.
- Для `stellenangebote` фиксируем факт появления записи в каждом запуске:
- событие `event_type=list_seen` в `stellenangebote_history` с `run_id` и `seen_at`.
- Для `list_seen` включен TTL (по умолчанию `540` дней, настраивается через `history_ttl_days.list_seen` или `STELLENANGEBOTE_LIST_SEEN_TTL_DAYS`).

## Код и читаемость
- Python 3.11+.
- Стиль: PEP8, короткие функции, минимальная вложенность.
- Имена: понятные, предметные, без лишних сокращений.
- Код должен быть самодокументируемым.
- Комментарии добавляем только там, где логика неочевидна для junior.
- Дублирование общей инфраструктуры (конфиг, Mongo, логирование, даты, ретраи) выносим в общие модули.

## Режим "для новичка" (постоянное правило)
- Если участок кода потенциально сложен для начинающего, добавляем короткие комментарии на русском:
- что именно делает блок;
- какую проблему он решает в проекте;
- почему выбран именно такой подход.
- Приоритет: самодокументируемые имена и простая структура функций; комментарии дополняют код, а не дублируют каждую строку.
- Для новых модулей и CLI-команд добавляем понятные docstring/описания входов и выходов.
- Для нетривиальных конфигов добавляем пояснение ключей в документации (и/или рядом с кодом чтения конфига).

## Логирование, таймауты, ретраи
- Логирование обязательно во всех pipeline-скриптах.
- Таймауты обязательны для всех внешних HTTP-запросов.
- Ретраи обязательны для временных ошибок сети/API с ограничением числа попыток.
- Логи должны быть единообразными по формату и уровням.

## Запуск (минимум)
1. Установить зависимости:
```bash
pip install -r requirements.txt
```
2. Подготовить `.env` (минимум):
```dotenv
MONGODB_URI=...
OPENAI_API_KEY=...
```
3. Запуск пайплайнов:
```bash
python3 -m app.job_list_collector
python3 -m app.job_details_collector
python3 -m app.analyze_jobs
```
4. Импорт профиля:
```bash
python3 tools/import_profiles.py --file conf/profiles/default.profile.json
```
5. Тесты:
```bash
pytest -q
```

## Важно про пути конфигов
- Целевой стандарт: `conf/`.
- Используем только `conf/...`.
- Обратная совместимость с `config/...` отключена.

## Процесс для крупных изменений
- Для больших задач сначала пишем план в `PLANS.md`.
- После этого выполняем работу пошагово по плану.
- По завершении этапа фиксируем статус и результат в `PLANS.md`.

## Обязательные действия в начале сессии
- Проверить `git status` и понять, какие изменения уже не закоммичены.
- Проверить, есть ли активные планы в `PLANS.md` по текущей задаче.
- Если задача затрагивает конфиги/флаги, заранее определить:
  - какие ENV/CLI параметры появятся или изменятся;
  - какие файлы документации и examples должны быть обновлены.
