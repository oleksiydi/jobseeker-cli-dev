# PLANS.md

## Назначение
Файл для планирования крупных задач до начала реализации.
Правило: любые большие изменения сначала описываются здесь, затем выполняются по шагам.

## Когда задача считается большой
Задача относится к большой, если выполняется хотя бы одно условие:
- изменяется архитектура или структура модулей;
- затрагиваются несколько pipeline-скриптов;
- меняется схема данных/индексы MongoDB;
- добавляются новые зависимости;
- есть риск регрессий в прод-процессе.

## Правила ведения
- Не начинать реализацию большой задачи без записи плана в этот файл.
- План должен быть пошаговым, с проверками и откатом.
- После каждого этапа обновлять статус и фиксировать факт выполнения.
- Если условия изменились, сначала обновить план, потом код.
- Планы писать коротко и однозначно, без воды.

## Общий ориентир (roadmap)

### [MASTER-20260206] Рефакторинг ETL/ELT и анализатора

Контекст:
- Цель: сделать кодовую базу поддерживаемой, идемпотентной и предсказуемой для специалистов разных уровней.
- Ограничения:
- Не менять названия коллекций `stellenangebote`, `jobdetails`, `analysen`, `profiles`.
- Использовать `requests + Session`.
- Feature flags: конфиг + ENV override.
- Конфиги: стандартная директория `conf/` (используется как единственный источник).
- В основных коллекциях хранить только актуальные данные, историю переносить в дополнительные коллекции.

Этапы:
1. Унификация инфраструктуры (`config/logging/mongo/time`) без изменения бизнес-логики.
2. Миграция конфигов на `conf/` как единственный источник.
3. Идемпотентный сбор `stellenangebote` (hash + diff + минимальные update).
4. Идемпотентный сбор `jobdetails` (hash + diff + retries + Session).
5. Версионирование `analysen` по `input_hash` и `version`, пропуск дублей.
6. Вынос истории в дополнительные коллекции и удаление хранения истории внутри основных документов.
7. Валидация конфигов/моделей и усиление типизации.
8. Минимально достаточные тесты (unit + integration) на критичные сценарии.
9. Поэтапный rollout с флагами и метриками `new/updated/skipped/errors`.

Критерии успеха:
- Повторный запуск пайплайнов не создает лишние записи.
- Новая версия анализа появляется только при реальном изменении входа.
- Основные коллекции содержат только текущее состояние.
- Конфиги читаются из `conf/`.
- Код и логи остаются читаемыми и единообразными.

Шаги:
1. Создать общий конфиг-модуль и единый интерфейс доступа к настройкам.
Критерий готовности: все три pipeline-скрипта читают конфиг через один модуль; прямые дублирующие функции `load_config` удалены.
Риски: несовместимость с текущими ENV override.
Откат: вернуть локальные функции загрузки конфига в скриптах.

2. Создать единый модуль Mongo-подключения.
Критерий готовности: во всех скриптах подключение к Mongo идет через `app/db/mongo.py`; поведение по `MONGODB_URI` и `db_name` документировано и единообразно.
Риски: разные ожидания по приоритету `config` и ENV.
Откат: вернуть старый способ подключения в конкретном скрипте.

3. Создать единый модуль логирования.
Критерий готовности: каждый скрипт получает логгер через общий helper; формат/уровни логов согласованы.
Риски: изменение формата логов может усложнить чтение старых логов.
Откат: временно оставить старый `logging.basicConfig` в точках входа.

4. Создать модуль времени и перенести туда парсинг/UTC-утилиты.
Критерий готовности: `parse_dt` и UTC-функции не дублируются; скрипты используют единые helpers.
Риски: регрессия на нестандартных форматах даты.
Откат: вернуть прежний парсер в `job_details_collector.py`.

5. Переподключить скрипты к новым модулям без изменения бизнес-правил.
Критерий готовности: команды запуска выполняются, поведение сбора/анализа логически не изменилось.
Риски: скрытые зависимости от локальных реализаций.
Откат: пофайловый возврат к предыдущей версии.
