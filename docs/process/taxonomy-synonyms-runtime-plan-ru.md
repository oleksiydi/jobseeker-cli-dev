# План Этапа: Словарная Нормализация Без LLM в Runtime

Audience: `Human + AI`  
Status: `draft-for-implementation`  
Last updated: `2026-03-23`

## Связанные документы

- `docs/process/taxonomy-plan-practical-value-assessment-ru.md` — внешняя практическая, продуктовая и исследовательская оценка плана.
- `docs/process/taxonomy-synonyms-codex-implementation-plan-ru.md` — execution-ready план реализации для пошаговой работы в Codex/VS Code.

## Цель этапа

Построить словарный контур нормализации вакансий и профилей, который работает без LLM в runtime: детерминированно, повторяемо, с понятным quality-control и возможностью масштабировать покрытие.

## Почему это нужно сейчас

Текущий extraction уже дает полезные артефакты, но в них встречаются абстракции/переводы, которые плохо подходят для детерминированного runtime lookup (пример: немецкий source-фрагмент, английский canonical).

Нужен контур, где:
- runtime не вызывает LLM;
- equivalence DE/EN учитывается через словарь синонимов;
- сложные случаи разбираются автоматически (LLM-валидация), без ручной приемки.

## Жесткие ограничения этапа

- Без ручной редакции и ручной приемки словаря.
- LLM разрешен только в офлайн-пайплайне построения/валидации.
- Runtime-нормализация профиля/вакансии должна быть детерминированной.
- Все изменения словаря версионируются и трассируются.

## Ключевые принципы

1. `Extractive-first`: термин в raw-слое должен быть максимально близок к реальному тексту вакансии.
2. `Domain-aware equivalence`: синонимы учитываются в рамках домена, а не глобально.
3. `Auto-governance`: приемка только через автоматические правила и LLM-adjudication для сложных случаев.
4. `Offline semantic help`: embeddings используются только офлайн для расширения alias-слоя.
5. `Stable runtime`: release-слой словаря работает без LLM и без вероятностных решений.

## Термины и слои

- `canonical`: стабильный внутренний ключ понятия.
- `alias`: реальная форма из текстов (DE/EN/варианты написания).
- `taxonomy`: категории/facet/skill_class и domain-структура canonical-терминов.
- `synonyms`: alias -> canonical с domain-aware ограничением.
- `release`: проверенный слой для runtime.
- `auto`: рабочий слой после авто-приемки, до freeze/release.

## Фактическая база (по тестовым прогонам)

### Наблюдения по reliability

- `mistral-nemo-300`: 300 ok, 2 transport error, полноценный aggregate.
- `mistral-small-3.2-24b-300`: 100 ok, 40 error, прогон неполный.
- `gpt-5-nano-30`: 30 error, термины не собраны.
- `grok-4-fast-300`: 33 error (rate-limit upstream), термины не собраны.

### Базовые метрики для расчетов масштаба (из `mistral-nemo-300`)

- 300 вакансий -> 2928 term rows.
- 1959 unique term_key в aggregate.
- 545365 total tokens в LLM calls.
- 0.053511 USD суммарная стоимость (по provider usage в логе).
- Средний `elapsed_ms` на LLM-call ~ 47793 ms.

## Целевая архитектура (без ручной приемки)

### Слой A: Extraction raw

Назначение:
- собрать term candidates и source evidence.

Выход:
- `vacancy_terms.<run>.jsonl`
- `vacancy_taxonomy_llm_calls.<run>.jsonl`
- `vacancy_taxonomy_process.<run>.jsonl`
- `vacancy_taxonomy_checkpoint.<run>.jsonl`

### Слой B: Taxonomy aggregate

Назначение:
- агрегировать term_key/canonical/domain/category/facet/skill_class.

Выход:
- `taxonomy_domain_aggregate.<run>.json`

### Слой C: Synonyms candidate (auto)

Назначение:
- построить alias-кандидаты из реальных форм текста;
- применить deterministic normalization rules;
- отсечь шум и конфликты.

Выход:
- `synonyms.candidates.jsonl` (внутренний технический артефакт)

### Слой D: LLM adjudication (только сложные кейсы)

Назначение:
- разобрать ambiguous/conflicting пары alias->canonical;
- автоматически принять/отклонить.

Выход:
- `synonyms.adjudicated.jsonl`

### Слой E: Offline embeddings expansion

Назначение:
- предложить дополнительные alias по семантической близости;
- принять только при порогах similarity и domain consistency.

Выход:
- `synonyms.embeddings_candidates.jsonl`

### Слой F: Publish runtime dictionaries

Назначение:
- собрать итоговые `taxonomy.auto/release` и `synonyms.auto/release`.

Выход:
- `conf/normalization/taxonomy.auto.json`
- `conf/normalization/synonyms.auto.json`
- (после freeze) `taxonomy.release.json`, `synonyms.release.json`

## Полный рабочий процесс (end-to-end)

1. Запуск extraction на корпусе вакансий.
2. Агрегация taxonomy.
3. Генерация alias-кандидатов deterministic-правилами.
4. Применение auto-accept/auto-reject правил.
5. LLM-adjudication только для сложных случаев.
6. Offline embeddings expansion только для unresolved/long-tail.
7. Повторный auto-gate.
8. Публикация auto-слоя.
9. Freeze в release-слой.
10. Runtime использует только release+auto merge без LLM.

## Правила приемки без человека

### Auto-accept (пример)

- alias наблюдается >= N раз;
- domain conflict отсутствует;
- similarity к canonical выше порога;
- нет коллизии с другим canonical в том же domain.

### Auto-reject (пример)

- alias слишком короткий/шумовой;
- конфликт category/facet/skill_class с устойчивой majority;
- низкая confidence + низкая поддержка по источникам.

### LLM-adjudication queue

В очередь отправляются только:
- alias с конфликтом canonical;
- cross-domain неоднозначность;
- высокочастотные, но неразрешенные кандидаты;
- критичные для runtime unknown, попавшие выше порога частоты.

## Что делать с английскими формами

- EN и DE формы сохраняются как `alias`, если реально встречаются в текстах.
- Эквивалентность EN<->DE задается в domain-aware synonyms.
- Canonical остается внутренним стабильным ключом.
- Runtime матчит по alias-слою детерминированно.

## Масштабирование: 20k, 100k, 700k вакансий

Оценки рассчитаны от фактического прогона `mistral-nemo-300`.

### Объем данных

- 20k: ~195k term rows.
- 100k: ~976k term rows.
- 700k: ~6.83M term rows.

### Оценка unique term_key (Heaps-law range)

- 20k: ~13k–24k.
- 100k: ~27k–64k.
- 700k: ~64k–205k.

### Оценка LLM токенов/стоимости (baseline pass)

- 20k: ~36.4M токенов, ~$3.57.
- 100k: ~181.8M токенов, ~$17.84.
- 700k: ~1.27B токенов, ~$124.86.

Примечание:
- это baseline first-pass;
- LLM-adjudication обычно добавляет ~10%..40% к токенам/стоимости.

### Оценка времени (если запускать строго последовательно)

- 20k: ~11 дней.
- 100k: ~55 дней.
- 700k: ~387 дней.

Вывод:
- главный bottleneck масштаба — latency/throughput API;
- нужен параллельный worker-pool + rate-limit aware retries + checkpoint resume.

## Требования к инфраструктуре

### Для runtime (без LLM)

- 20k уровень: 4 vCPU, 16 GB RAM, SSD.
- 100k уровень: 8 vCPU, 16-32 GB RAM, NVMe.
- 700k уровень: 8-16 vCPU, 32-64 GB RAM, NVMe.

### Для offline построения словаря

- orchestrator: 8-16 vCPU, 32 GB RAM;
- storage под артефакты: минимум 200 GB (лучше 500 GB+ для 700k);
- embeddings pass:
  - можно CPU-only (медленно),
  - рекомендован 1 GPU с 24 GB VRAM для ускорения.

## Узкие места и меры снижения риска

1. Лингвистический дрейф extraction.
Мера:
- enforce extractive-first;
- reject translated-only aliases без source-связи.

2. Domain collisions.
Мера:
- domain-aware mapping обязателен;
- запрет auto-accept при междоменном конфликте.

3. Взрыв объема long-tail aliases.
Мера:
- frequency thresholds;
- TTL/архив для низкочастотных кандидатов;
- отдельный pending слой.

4. Provider rate limits и нестабильность.
Мера:
- checkpoint/resume;
- параллельность с backoff;
- fallback provider/model policy.

## Метрики готовности этапа

- Runtime unknown-rate снижается от батча к батчу.
- Детерминированность: повторный прогон на том же словаре дает идентичный результат.
- Доля auto-accepted кандидатов растет без деградации качества.
- Доля unresolved после adjudication не превышает заданный порог.
- SLA runtime без LLM выдерживается.

## Definition of Done

- В runtime нет LLM-вызовов для нормализации терминов.
- `taxonomy.release + synonyms.release` формируются полностью автоматизированно.
- Процесс выдерживает масштаб минимум 20k без ручной приемки.
- Для 100k есть подтвержденный рабочий throughput-план.
- Документация и операционные команды воспроизводимы на чистой машине.

## Детальный пошаговый план реализации (принятая схема)

### Фаза A. Подготовка и фиксация контракта

#### Шаг 1. Зафиксировать контракт данных и версий
1. Название шага: Зафиксировать контракт данных и версий.
2. Задача шага: определить финальные форматы raw/aggregate/synonyms/release артефактов и правила версионирования.
3. Проблема: без жесткого контракта разные этапы будут несовместимы и неповторяемы.
4. Как решает проблему: утверждаются schema-правила, naming convention run-артефактов, правила merge `release + auto`, version fields и provenance fields.
5. Результат: единый контракт артефактов и формат версий для всех этапов.
6. Условия приемки: все задействованные JSON/JSONL форматы валидируются схемами; есть один документ с контрактом и перечнем обязательных полей.

#### Шаг 2. Подготовить операционный контур запуска
1. Название шага: Подготовить операционный контур запуска.
2. Задача шага: обеспечить reproducible запуск больших прогонов с checkpoint/resume и безопасными retry.
3. Проблема: длинные прогоны уязвимы к 429/сетевым ошибкам и могут терять прогресс.
4. Как решает проблему: настраиваются checkpoint-path, process-log, llm-calls-log, idempotent resume и лимиты retry/backoff.
5. Результат: стабильно перезапускаемый pipeline без ручного восстановления.
6. Условия приемки: принудительное прерывание и повторный запуск продолжают прогресс без дублирования записей и без потери уже обработанных вакансий.

### Фаза B. Extraction raw (LLM офлайн)

#### Шаг 3. Перевести extraction в режим extractive-first
1. Название шага: Перевести extraction в режим extractive-first.
2. Задача шага: сделать так, чтобы термины были максимально близки к реальному тексту вакансии.
3. Проблема: абстрактные/переведенные термины ухудшают детерминированную нормализацию в runtime.
4. Как решает проблему: ужесточается prompt/policy, добавляются проверки на связь `term` с `context_phrase`, запрещаются translated-only aliases без source evidence.
5. Результат: raw-слой содержит реальные surface forms, пригодные для словаря.
6. Условия приемки: доля записей без очевидной связи term<->context_phrase ниже заданного порога; schema-validation проходит без ошибок.

#### Шаг 4. Выполнить пилотный прогон 20k вакансий
1. Название шага: Выполнить пилотный прогон 20k вакансий.
2. Задача шага: получить первую репрезентативную базу raw терминов для полноценной автоматической сборки словаря.
3. Проблема: на 300 вакансиях недостаточно long-tail и междоменных пересечений.
4. Как решает проблему: запускается extraction на 20k с checkpoint/resume, фиксируются токены, latency, error-rate и coverage по доменам.
5. Результат: полный набор raw-артефактов для 20k.
6. Условия приемки: `run_finished` присутствует, processed покрывает целевой объем, error-rate и retry-budget в допустимых пределах.

### Фаза C. Taxonomy aggregate

#### Шаг 5. Построить агрегат taxonomy и canonical-кандидаты
1. Название шага: Построить агрегат taxonomy и canonical-кандидаты.
2. Задача шага: агрегировать term_key/canonical/category/facet/domain и подготовить основу для synonyms слоя.
3. Проблема: raw-строки без агрегации не дают устойчивой структуры понятий.
4. Как решает проблему: формируется `taxonomy_domain_aggregate`, считаются votes/count/confidence/source_refs_count, выделяются устойчивые canonical-кандидаты.
5. Результат: структурированный агрегат понятий по доменам.
6. Условия приемки: aggregate schema валиден; ключевые статистики согласованы с raw (term_rows, source_refs, domain distribution).

#### Шаг 6. Проверить междоменные коллизии canonical
1. Название шага: Проверить междоменные коллизии canonical.
2. Задача шага: выявить конфликтные canonical и alias между доменами.
3. Проблема: один и тот же alias может иметь разные смыслы в разных доменах.
4. Как решает проблему: строится collision-report по `(alias, domain, canonical)` и выделяются ambiguous кандидаты для следующего этапа.
5. Результат: список конфликтных случаев и чистый набор non-conflict кандидатов.
6. Условия приемки: сформирован machine-readable collision-report; все конфликтные записи помечены статусом `needs_adjudication`.

### Фаза D. Synonyms без ручной приемки

#### Шаг 7. Сгенерировать deterministic alias-кандидаты
1. Название шага: Сгенерировать deterministic alias-кандидаты.
2. Задача шага: расширить alias-слой правилами нормализации и вариантами написания.
3. Проблема: реальные формулировки отличаются по регистру, дефисам, umlaut и служебным словам.
4. Как решает проблему: применяются deterministic transform rules (casefold, hyphen/space, umlaut variants, cleanup префиксов), результат сохраняется в candidate-слой.
5. Результат: расширенный список alias-кандидатов с provenance.
6. Условия приемки: для каждого alias есть trace к source; дубликаты дедуплицированы; transform-rules покрыты тестами.

#### Шаг 8. Применить auto-accept/auto-reject gate
1. Название шага: Применить auto-accept/auto-reject gate.
2. Задача шага: автоматически принять очевидно корректные и отклонить очевидно шумовые кандидаты.
3. Проблема: без массовой авто-фильтрации объем ambiguous кейсов становится неуправляемым.
4. Как решает проблему: используются пороги по частоте, confidence, domain-consistency, collision flags, noise heuristics.
5. Результат: три статуса кандидатов — `accepted`, `rejected`, `needs_adjudication`.
6. Условия приемки: доля auto-classified записей выше целевого порога; качество на контрольной выборке не деградирует.

#### Шаг 9. Выполнить LLM-adjudication для сложных случаев
1. Название шага: Выполнить LLM-adjudication для сложных случаев.
2. Задача шага: автоматически разобрать ambiguous/conflict кейсы без участия человека.
3. Проблема: без adjudication спорные записи останутся unresolved и снизят coverage runtime.
4. Как решает проблему: отдельный adjudication prompt/contract принимает решение `accept/reject/remap` с обоснованием и confidence.
5. Результат: закрытие очереди `needs_adjudication` до заданного остатка.
6. Условия приемки: unresolved-доля ниже установленного порога; решения записаны в machine-readable adjudication log.

#### Шаг 10. Добавить offline embeddings expansion
1. Название шага: Добавить offline embeddings expansion.
2. Задача шага: добрать long-tail alias, которые не покрылись deterministic правилами.
3. Проблема: часть семантических вариантов не совпадает строково и не проходит rule-only этап.
4. Как решает проблему: для unresolved кандидатов строятся nearest-neighbor предложения в embedding space внутри домена; далее повторно применяется gate/adjudication.
5. Результат: дополнительный слой валидных alias для long-tail.
6. Условия приемки: coverage растет, а collision-rate не выходит за допустимые пределы; все новые alias имеют provenance.

#### Шаг 11. Сформировать `synonyms.auto` и технический отчет качества
1. Название шага: Сформировать `synonyms.auto` и технический отчет качества.
2. Задача шага: собрать итоговый auto-слой синонимов и зафиксировать метрики качества.
3. Проблема: без отчетности невозможно контролировать регрессии и принимать release-решения.
4. Как решает проблему: публикуются `synonyms.auto` и quality-report (unknown-rate, collision-rate, auto-accept ratio, unresolved ratio).
5. Результат: готовый auto-слой и формальная база для freeze.
6. Условия приемки: все целевые quality thresholds достигнуты; артефакты валидны и воспроизводимы.

### Фаза E. Публикация и runtime интеграция

#### Шаг 12. Freeze словаря в release-слой
1. Название шага: Freeze словаря в release-слой.
2. Задача шага: закрепить стабильную словарную версию для runtime.
3. Проблема: без freeze runtime будет зависеть от нестабильного промежуточного состояния.
4. Как решает проблему: выполняется controlled promote `auto -> release` с фиксацией версии, даты и changelog.
5. Результат: `taxonomy.release.json` и `synonyms.release.json`.
6. Условия приемки: release-артефакты валидны, версионированы и пригодны к rollback.

#### Шаг 13. Подключить release+auto в runtime и доказать отсутствие LLM
1. Название шага: Подключить release+auto в runtime и доказать отсутствие LLM.
2. Задача шага: включить словарный контур в реальные pipeline шаги нормализации профилей/вакансий.
3. Проблема: словарь может остаться “офлайн артефактом” без практического эффекта в рабочем pipeline.
4. Как решает проблему: runtime использует merged loader, включаются интеграционные проверки на отсутствие LLM-вызовов в нормализации.
5. Результат: production-ready deterministic normalization path.
6. Условия приемки: e2e smoke подтверждает нормализацию без LLM; результаты повторяемы на одинаковом входе.

### Фаза F. Наблюдаемость и масштабирование

#### Шаг 14. Ввести мониторинг качества и регрессий
1. Название шага: Ввести мониторинг качества и регрессий.
2. Задача шага: непрерывно контролировать практическое качество словаря после релиза.
3. Проблема: качество может деградировать незаметно при росте корпуса и доменного сдвига.
4. Как решает проблему: в nightly/report контур добавляются метрики unknown-rate, mapping stability, collision-rate, drift по доменам.
5. Результат: раннее обнаружение регрессий и триггеры на пересборку.
6. Условия приемки: мониторинговые метрики публикуются регулярно; есть пороги alert и процедура реакции.

#### Шаг 15. Масштабировать реализацию 20k -> 100k -> 700k
1. Название шага: Масштабировать реализацию 20k -> 100k -> 700k.
2. Задача шага: перевести схему из pilot в производственный масштаб без потери качества и устойчивости.
3. Проблема: при росте объема растут latency, rate-limit риски и стоимость adjudication.
4. Как решает проблему: поэтапный rollout, настройка worker-pool и retry-budget, контроль cost/token throughput и quality gates на каждом уровне.
5. Результат: рабочий масштабируемый контур словаря на целевых объемах.
6. Условия приемки: для каждого масштаба достигнуты SLA по времени, стоимости и качеству; переход к следующему масштабу разрешается только после прохождения gate-критериев.
