# Jobcenter API Audit (2026-02-22)

Приоритет: HIGH
Статус: открыто, требуется архитектурное решение

## Контекст
Проверка пайплайнов:
- `app/job_list_collector.py`
- `app/job_details_collector.py`
- `app/analyze_jobs.py`
- `app/build_job_index.py`

## High-priority риски

1. Нет retry в `job_list_collector` на уровне списка вакансий.
- Симптом: при временной сетевой/HTTP ошибке страница ломает цикл и run завершается частично.
- Последствие: неполный снимок рынка за запуск, пропуски обновлений, нестабильная деактивация отсутствующих вакансий.

2. Некорректная уникальность в `analysen` для мультипрофильного режима.
- Сейчас уникальность опирается на `(referenznummer, input_hash)`, без `candidate_profile_key`.
- Последствие: коллизии/потеря аналитики, если используются несколько профилей кандидата.

3. Несогласованная семантика `is_active` между пайплайнами.
- `build_job_index`: только `is_active=True`.
- `analyze_jobs` и `job_details_collector`: трактуют как активные документы с `is_active != False`.
- Последствие: одна и та же вакансия может анализироваться, но не индексироваться.

4. Риск полной остановки `job_details_collector` от единичной ошибки MongoDB.
- Внутри цикла по вакансиям нет локальной изоляции ошибок записи.
- Последствие: один transient write error роняет весь batch/run.

## Принципиальные проблемы концепции (архитектурный уровень)

1. Нет единого "source of truth" для жизненного цикла вакансии.
- `is_active` сейчас вычисляется косвенно по list-run, а не как отдельный state machine.
- Разные скрипты читают это поле по-разному.

2. Смешаны две разные модели активности.
- "Актуальна в листинге" (видим в выдаче API сейчас).
- "Актуальна для downstream-процессов" (анализ/индексация/поиск).
- Эти модели не разведены явно, поэтому появляются логические расхождения.

3. Неполный run интерпретируется почти так же, как полный.
- Есть флаг `completed_full_scan`, но нет системной деградации (например, lock состояния run, режим read-only для downstream, отдельный health сигнал).

4. Сильная зависимость от удаленных timestamp как единственного критерия свежести.
- При аномалиях источника (timestamp не обновился, округлился, отстал) можно пропустить реальные изменения контента.

## Что нужно решить архитектурно

1. Ввести единый контракт активности вакансии.
- Определить и задокументировать значения состояния (например: `active`, `missing_soft`, `missing_hard`, `archived`).
- Все пайплайны должны читать этот контракт одинаково.

2. Разделить состояние "видимости в листинге" и "готовности к downstream".
- Ввести отдельные поля/флаги или отдельную коллекцию состояния.

3. Зафиксировать политику деградации при частичном run.
- Что блокируем, что разрешаем, как сигнализируем оператору.

4. Пересмотреть ключ уникальности для `analysen` с учетом профиля.
- Уникальность должна быть консистентной с реальным бизнес-ключом анализа.
