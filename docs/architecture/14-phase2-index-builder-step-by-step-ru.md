# Phase 2: Index Builder (простыми словами, пошагово)

## Зачем вообще нужен этот этап

На этом этапе мы готовим “поисковую базу по смыслу”:
- берём вакансии из MongoDB;
- превращаем их в удобные текстовые куски (чанки);
- считаем для них эмбеддинги (векторы);
- сохраняем в Qdrant.

После этого система сможет быстро находить релевантные вакансии не только по словам, но и по смыслу.

## Главная идея этапа

Не пересчитывать всё каждый раз, а обновлять только то, что реально изменилось.

Именно это даст:
1. меньше нагрузки на CPU;
2. быстрее ночной прогон;
3. предсказуемое время работы.

## Что будет на входе

Из MongoDB берём:
1. `stellenangebote` (meta);
2. `jobdetails` (details).

Для каждой `referenznummer` собираем один “объединённый документ вакансии”.

## Что будет на выходе

1. В Qdrant:
- чанки вакансии + их векторы + полезные метаданные.

2. В MongoDB (служебные поля индексации):
- `embedding_input_hash`
- `embedding_model`
- `chunking_version`
- `preprocess_version`
- время последней индексации

Эти поля нужны, чтобы понимать: надо ли пересчитывать вакансию или можно пропустить.

## Пошаговый сценарий

### Шаг 1. Прочитать конфиг и проверить зависимости

Что делаем:
1. Читаем `conf/app.json` + ENV override.
2. Проверяем, что Qdrant доступен.
3. Проверяем, что нужная коллекция Qdrant существует (или создаём).

Зачем:
- чтобы не падать в середине обработки;
- чтобы сразу увидеть проблемы окружения.

Готово, если:
- healthcheck Qdrant успешен;
- коллекция доступна.

### Шаг 2. Получить “актуальные вакансии” из Mongo

Что делаем:
1. Берём актуальные записи из `stellenangebote`.
2. Джойним с `jobdetails` по `referenznummer`.
3. Собираем единый объект вакансии.

Зачем:
- модель и индекс должны видеть целостную вакансию, а не разрозненные куски.

Готово, если:
- на каждую `referenznummer` есть единая merged-структура.

### Шаг 3. Нормализовать текст

Что делаем:
1. Убираем служебный мусор (лишние пробелы, шумные спецсимволы).
2. Приводим текст к стабильному виду (чтобы одинаковый текст давал одинаковый hash).
3. Исключаем служебные поля (`_id`, `*_hash`, `*_dt`, и т.п.) из текста для эмбеддинга.

Зачем:
- уменьшить “ложные изменения”;
- улучшить качество чанков.

Готово, если:
- одинаковый смысловой текст даёт одинаковый нормализованный результат.

### Шаг 4. Разбить на предложения (spaCy)

Что делаем:
1. Прогоняем описание вакансии через spaCy.
2. Получаем корректные границы предложений (особенно важно для немецкого).

Зачем:
- semantic chunking работает качественно только если предложения выделены правильно.

Готово, если:
- предложения не “рвутся” в неправильных местах.

### Шаг 5. Сделать semantic chunking

Что делаем:
1. Берём соседние предложения.
2. Объединяем их в один чанк, если они близки по смыслу.
3. Разделяем при смене темы.

Важно:
- `semantic_*` параметры управляют смысловой логикой.
- `hard_*` и `fallback_overlap_chars` — это защитные ограничения, а не основная логика.

Зачем:
- получить чанки, которые несут цельные смысловые блоки.

Готово, если:
- чанки читаются как законченные фрагменты (“требования”, “задачи”, “условия” и т.п.).

### Шаг 6. Собрать текст для эмбеддинга и посчитать hash

Что делаем:
1. Формируем канонический текст вакансии (только полезные поля).
2. Считаем `embedding_input_hash`.
3. Сравниваем с тем, что уже сохранено в Mongo.

Правило skip:
- если `embedding_input_hash`, `embedding_model`, `chunking_version`, `preprocess_version` не изменились, вакансию пропускаем.

Зачем:
- инкрементальность и экономия времени.

Готово, если:
- есть понятный список `changed` и `skipped`.

### Шаг 7. Посчитать эмбеддинги

Что делаем:
1. Для изменённых вакансий считаем векторы по чанкам.
2. При необходимости считаем summary-вектор вакансии.

Зачем:
- чанк-уровень нужен для точного поиска;
- summary-уровень полезен для агрегирования на уровне вакансии.

Готово, если:
- на каждый чанк есть корректный вектор нужной размерности.

### Шаг 8. Записать в Qdrant (upsert)

Что делаем:
1. Для каждого чанка делаем upsert в Qdrant.
2. В payload пишем метаданные:
- `referenznummer`
- `chunk_id`
- `chunk_index`
- `section_label` (если есть)
- служебные версии

Зачем:
- потом можно фильтровать и объяснять, почему найдена вакансия.

Готово, если:
- все changed-вакансии обновлены в Qdrant без дублей.

### Шаг 9. Обновить служебные поля в Mongo

Что делаем:
1. Сохраняем новые:
- `embedding_input_hash`
- версии моделей/чанкинга/препроцессинга
- `indexed_at`

Зачем:
- следующая итерация сможет правильно решить, что пересчитывать.

Готово, если:
- повторный прогон без изменений почти всё пропускает.

### Шаг 10. Сформировать отчёт прогона

Что делаем:
1. Логируем и/или сохраняем метрики:
- сколько вакансий рассмотрели;
- сколько `changed`;
- сколько `skipped`;
- сколько времени занял каждый этап.

Зачем:
- понимать, укладываемся ли в целевые 8-12 часов на CPU.

Готово, если:
- есть прозрачный отчёт по батчу.

## Что будет считаться “успешным Phase 2”

1. Повторный запуск без изменений почти ничего не пересчитывает.
2. Для изменённых вакансий обновления попадают в Qdrant.
3. Есть стабильный отчёт по `changed/skipped/time`.

## Частые ошибки и как их избежать

1. Слишком много “ложных изменений”.
- Причина: нестабильная нормализация текста.
- Решение: фиксировать канонизацию и исключать шумные поля.

2. Плохие чанки.
- Причина: резка только по символам без смысловой проверки.
- Решение: semantic chunking + корректная сегментация предложений.

3. Долгая обработка.
- Причина: пересчёт всех вакансий в каждом запуске.
- Решение: строгий skip по hash и версиям.

## Мини-чеклист перед началом реализации

1. Qdrant запущен и проходит healthcheck.
2. В `matching`-конфиге выставлены:
- модель эмбеддинга;
- стратегия chunking;
- версии `chunking/preprocess`.
3. Определён формат merged-вакансии и канонического текста.
4. Определён набор метрик батча.
