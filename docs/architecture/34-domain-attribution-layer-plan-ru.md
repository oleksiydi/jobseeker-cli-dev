# 34 Domain Attribution Layer Plan (RU)

Тип документа: `planned`

## Что уже есть сейчас

Сейчас система хорошо делает базовый подбор:

- поиск по запросу;
- учет профиля кандидата;
- фильтры;
- retrieval + rerank.

Сценарий Jobcenter уже поддерживает множественный `beruf` в одном запросе, например IT + медицина:

`https://www.arbeitsagentur.de/jobsuche/suche?angebotsart=1&beruf=Fachinformatiker%2Fin%20-%20Systemintegration;Medizinische%2Fr%20Fachangestellte%2Fr`

Это полезно, но текущий движок может переоценивать общие термины без учета доменного контекста.

## Проблема, которую хотим закрыть

Одинаковые слова в разных профессиях могут значить разное:

- `Analyse`
- `Diagnose`
- `Test`
- `Simulation`
- `Monitoring`
- `Training`
- `Dokumentation`
- `Kontrolle`
- `Planung`

Без отдельного доменного слоя такие слова дают шум: совпадение по термину есть, а совпадение по сути профессии неполное.

## Цель улучшения

Поднимать выше вакансии, где есть одновременно:

- совпадение по роли/навыкам;
- совпадение по домену отрасли;
- совпадение по фактическому опыту кандидата в смежной области.

## Пример (разобранный кейс)

Профиль кандидата:

- 5 лет разработки;
- опыт разработки медицинских диагностических систем;
- сильный IT-бэкграунд.

Вакансия:

- разработчик медицинской системы (например, УЗИ);
- часть требований IT-типовые, часть строго медицинские.

Ожидаемое поведение целевой версии:

- вакансия ранжируется высоко не только по общему IT-сходству,
- а за счет комбинации `разработка + медицинский домен`.

## Планируемый отдельный слой

Перед основной нормализацией/финальным скорингом добавить `domain attribution`:

1. Для вакансии вычислять распределение по доменам (пример: `healthcare=0.72`, `it=0.28`).
2. Для профиля кандидата вычислять аналогичное распределение по опыту.
3. Считать `domain_overlap` как отдельный сигнал ранжирования.
4. В финальном скоринге комбинировать:
   - `role_fit`
   - `domain_overlap`
   - `evidence_fit` (факты опыта из профиля)
   - `preference_match` (пожелания кандидата)

## Почему делаем это отдельным слоем, а не ломаем текущую таксономию

- текущая таксономия `skills/tools/stack` уже работает стабильно;
- доменный слой можно внедрить поэтапно без регрессий;
- проще A/B сравнение качества (`до/после`) по понятным метрикам.

## Метрики успеха для внедрения слоя

- снижение `role/domain mismatch` в top-20;
- рост доли релевантных вакансий в смежных доменах;
- улучшение объяснимости: в выдаче видно, почему вакансия поднялась (не только по одному слову).

## Приоритет

Приоритет: `high`, но этап `post-baseline`.

То есть сначала сохраняем стабильность текущего пайплайна, затем внедряем доменный слой как контролируемое расширение.
