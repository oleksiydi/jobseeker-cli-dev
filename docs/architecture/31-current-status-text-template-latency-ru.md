# Текущий статус: шаблон текста, latency и сравнение сложности

## 1) “Разве у нас не сделано уже правильное формирование текста?”
Короткий ответ: **частично сделано**, но не для model-based rerank.

Что уже есть в текущем search:
1. Профиль сериализуется в `profile_text`.
2. Запрос формируется как `query_input_text`.
3. Для выдачи сохраняются `top_chunks`.
4. Есть fallback chunk_text, если текст чанка пустой.

Что **не сделано** для model-based rerank:
1. Нет отдельного стабильного `candidate_text`-шаблона именно под cross-encoder.
2. Нет inference reranker, который использует `(query, candidate_text)`.

Итог:
- подготовка данных есть;
- полноценный rerank-вход для модели нужно фиксировать отдельно.

## 2) Почему “мусорный текст” ломает качество
Если в `candidate_text` много шума:
- контакты,
- “подайте заявку”,
- юридические хвосты,
то модель начинает повышать нерелевантные вакансии.

Практическое правило:
1. Включать: `title`, `role`, 1-3 лучших смысловых чанка.
2. Ограничивать длину.
3. По возможности ослаблять/убирать административные хвосты.

## 3) Почему latency растет при reranker
### Сейчас (baseline)
- Базовый rerank — это формулы и легкая лексика.
- Быстро: почти нет тяжелого model inference на этапе rerank.

### С model-based rerank
- На каждый кандидат (например, 50) нужно запустить модель.
- Это десятки inference-вызовов (батчированных, но все равно тяжелых).
- Поэтому latency вырастает.

## 4) Насколько сложность выше, чем embedding + cosine
Условно:
1. **Embedding + cosine retrieval**:
- быстрый ANN-поиск по готовому индексу в Qdrant;
- сложность runtime чаще ближе к “дешевому запросу по индексу”.

2. **Cross-encoder rerank**:
- требует прогонять нейросеть по каждой паре `(query, candidate_text)`;
- сложность растет примерно линейно с числом кандидатов `N`;
- на CPU заметно тяжелее.

Интуитивно:
- retrieval = “быстрый фильтр”;
- rerank model = “дорогая экспертная проверка”.

## 5) Как держать latency под контролем
1. Rerank только top-N (обычно 20-100, не весь корпус).
2. Батчи (8/16/32, под железо).
3. Ограничение длины candidate_text.
4. Таймауты и fallback на baseline.
5. Кэширование (по возможности).

## 6) Рекомендуемый минимальный рабочий путь
1. Включить model rerank только на `top_n=50`.
2. Задать стабильный шаблон:
- `TITLE: ...`
- `ROLE: ...`
- `TOP_CHUNKS: ...`
3. Добавить fallback, если модель недоступна.
4. Прогнать benchmark “до/после” на фиксированном `queries.txt`.
5. Принять решение по trade-off `качество vs latency`.
