# Эмбеддинги и экономия LLM-запросов (с пояснениями)

## Цель документа

Этот документ описывает:
- что уже реализовано в `jobseeker-cli`;
- как добавить локальный семантический поиск по вакансиям через эмбеддинги;
- как снизить количество и стоимость вызовов LLM за счет этапа предварительного отбора.

Пояснение:
- `LLM` в проекте используется для содержательной оценки вакансии относительно профиля.
- Главная проблема: LLM-вызовы дорогие и медленные, если отправлять в анализ слишком много вакансий.
- Главная идея: сначала отобрать наиболее релевантные вакансии дешево и локально (embeddings), и только потом вызывать LLM.

Документ ориентирован на начинающих разработчиков и владельца системы.

## Что уже есть в системе (текущее состояние)

Система уже построена как последовательность ETL/ELT пайплайнов:

1. `app/job_list_collector.py`
- забирает список вакансий (meta) из внешнего API;
- делает идемпотентный upsert в `stellenangebote`;
- пишет события в `stellenangebote_history` (`list_seen`, `content_change`, `list_missing`, `list_restored`).

Пояснение:
- `идемпотентность` означает, что повторный запуск не дублирует данные и не ломает состояние.
- Это решает проблему нестабильных cron/ручных перезапусков.

2. `app/job_details_collector.py`
- берет только активные вакансии из `stellenangebote`;
- делает обязательный prefilter по датам (`modifikationsTimestamp` vs `jobdetails.aenderungsdatum`);
- вызывает API деталей только для кандидатов, где есть шанс обновления;
- обновляет `jobdetails` и пишет события в `jobdetails_history`.

Пояснение:
- Этот слой решает проблему лишней нагрузки на внешний API (меньше запросов, ниже риск rate-limit/блокировок).
- По сути это первый барьер экономии ресурсов до LLM.

3. `app/analyze_jobs.py`
- объединяет актуальные `meta + details`;
- добавляет профиль кандидата из `profiles` и prompt из `analysis_prompts`;
- считает `input_hash` по входу анализа (`meta + details + profile + prompt + model`);
- если такой `input_hash` уже есть в `analysen`, повторный LLM-вызов пропускается;
- при изменении входа создает новую версию в `analysen`.

Пояснение:
- `input_hash` это “отпечаток входа”. Если отпечаток не изменился, повторный LLM-анализ не нужен.
- Это второй барьер экономии, уже на уровне LLM.

Итог: в проекте уже реализована сильная база для экономии запросов (идемпотентность + hash-based skip на этапе анализа).

## Зачем добавлять эмбеддинги

Сейчас LLM-анализ вызывается для набора активных вакансий после джойна данных.  
Эмбеддинги добавляют промежуточный этап: быстрый локальный поиск релевантных вакансий по смыслу.

Это дает:
- меньше вызовов LLM (анализируем только top-K релевантных);
- ниже стоимость;
- быстрее полный цикл;
- лучше UX в поиске по профилю и свободному запросу.

Пояснение:
- Проблема без embeddings: даже при `input_hash` приходится проверять много кандидатов.
- Решение embeddings: сначала “дешевый смысловой фильтр”, затем “дорогой умный анализ LLM”.

## Базовые термины простыми словами

- `Embedding`: превращение текста в числовой вектор (список чисел), который отражает смысл.
- `Vector similarity` (обычно cosine): насколько два текста похожи по смыслу.
- `Dense search`: поиск по эмбеддингам (по смыслу).
- `Sparse/BM25`: классический поиск по словам и их частоте.
- `Hybrid search`: dense + sparse вместе.
- `Reranker`: второй этап, который точнее переставляет top-K результатов.

Пояснение:
- `Dense` решает проблему синонимов и перефразов.
- `Sparse` решает проблему точных терминов (редкие технологии, названия сертификатов, коды инструментов).
- `Hybrid` нужен, потому что по отдельности dense и sparse дают перекосы.
- `Reranker` нужен для повышения точности первых 10-20 результатов, которые уйдут в LLM или UI.

## Как разбивать тексты на части (chunking)

### Вакансия

Рекомендуемые чанки:
1. `title_chunk`: заголовок, уровень, тип занятости.
2. `about_chunk`: описание роли/компании.
3. `requirements_chunk`: требования, стек, язык, опыт.
4. `tasks_chunk`: обязанности.
5. `conditions_chunk`: локация, удаленка, зарплата/условия.

Правило размера:
- целевой диапазон примерно 300-800 слов на chunk;
- если блок длиннее, резать по абзацам с overlap 10-15%.

Пояснение:
- Chunking решает проблему “размывания смысла” в слишком длинном тексте.
- Если хранить только один огромный текст, релевантные сигналы (например, требования) теряются среди второстепенных деталей.

### Профиль

Рекомендуемые чанки:
1. `profile_summary_chunk`: кто кандидат и в чем сильные стороны.
2. `skills_chunk`: технологии, инструменты, методологии.
3. `experience_chunk`: релевантный опыт и проекты.
4. `constraints_chunk`: языки, локация, формат работы, ограничения.
5. `goal_chunk`: что кандидат ищет сейчас.

Пояснение:
- Такое разделение помогает явно учитывать ограничения и цели, а не только “общий красивый текст профиля”.
- Это особенно важно при фильтрах по языку/локации/формату работы.

### Запрос пользователя

Запрос обычно короткий, поэтому:
1. `query_main`: как ввел пользователь.
2. `query_expanded`: авторасширенный вариант на основе профиля (стек, язык, локация, seniority).

Пояснение:
- `query_expanded` решает проблему слишком коротких запросов вроде “data engineer remote”.
- Добавленный контекст из профиля повышает шанс найти действительно подходящие вакансии.

## Как экономить LLM-запросы с embeddings (целевой поток)

1. Построить/обновить векторный индекс вакансий локально.
2. Для нового user query посчитать query embedding.
3. Найти top-K вакансий по смыслу (и по фильтрам при необходимости).
4. На LLM отправлять только shortlist (например, top-20, а не все активные).
5. Сохранить итог анализа как сейчас в `analysen` с версионированием и `input_hash`.

Практический эффект: вместо анализа сотен вакансий LLM получает только десятки наиболее релевантных.

Пояснение:
- `векторный индекс` нужен для быстрого поиска по миллионам/сотням тысяч векторов.
- Без индекса поиск по каждому документу “в лоб” станет медленным.

## Варианты реализации

### Вариант 1: `sentence-transformers` + `faiss-cpu`

Плюсы:
- хорошее качество;
- быстрый локальный ANN-поиск;
- полностью офлайн.

Минусы:
- `faiss-cpu` иногда сложнее в установке на отдельных ОС/архитектурах.

Пояснение:
- Хорошо решает задачу “быстро и качественно без отдельной векторной БД”.
- Подходит, если команда готова к чуть более сложной установке.

### Вариант 2: `fastembed` + `numpy` (без векторной БД)

Плюсы:
- самый простой старт;
- минимум инфраструктуры;
- легко объяснить и развернуть.

Минусы:
- хуже масштабируется на больших объемах вакансий;
- поиск медленнее, чем ANN-индексы.

Пояснение:
- Это вариант “запустить быстро MVP”.
- Решает задачу простого входа, но не решает задачу роста.

### Вариант 3: локальный `Qdrant` + локальные эмбеддинги

Плюсы:
- лучший баланс простоты и масштабирования;
- быстрый ANN;
- payload-фильтры;
- удобно для гибридного поиска и дальнейшего роста.

Минусы:
- нужно поднимать отдельный сервис (Docker).

Пояснение:
- Это наиболее практичный путь для вашего проекта: можно стартовать просто и не упереться в потолок при росте данных.

## Рекомендованный стек (для универсальности DE/EN)

Минимально рекомендуемый продакшн-путь:
1. Эмбеддинги: `intfloat/multilingual-e5-base` (или `-small` для более слабого CPU).
2. Индекс: `Qdrant` локально.
3. Ранжирование: `hybrid search` (dense + sparse) + `reranker` на top-50.

Почему так:
- мультиязычность (немецкий + английский);
- меньше ручных словарей эквивалентности;
- лучше устойчивость к формулировкам и синонимам;
- надежнее для роста, чем чистый словарный подход.

Пояснение:
- Проблема проекта: нужен DE+EN и высокая универсальность.
- Этот стек решает ее лучше, чем попытка вручную описать эквивалентности для всех технологий.

## Про эквивалентности (`docker` <-> `podman`) без ручного "зоопарка"

Полностью без правил не бывает, но объем ручной работы можно резко снизить:

1. Делать гибридный поиск (dense + sparse).
2. Добавить reranker на финальный top-K.
3. Оставить только очень короткий слой нормализации общих сокращений (`k8s -> kubernetes`, `js -> javascript`).
4. Не строить большой ручной словарь "всех соответствий".

Пояснение:
- Большой словарь эквивалентностей быстро устаревает и сложно поддерживается.
- В этом проекте он создаст больше операционных проблем, чем пользы.

## Как система самообучается на `click/apply/skip`

Сигналы:
- `click`: слабый позитив (вакансия заинтересовала).
- `apply`: сильный позитив (вакансия очень релевантна).
- `skip`: негатив (показали, но не выбрали).

Применение:
1. Логировать события показа и действия пользователя.
2. Периодически калибровать веса формулы ранжирования (`dense/sparse/rerank`).
3. При достаточных данных периодически дообучать reranker на своих парах `(query+profile, job_text, label)`.

Это дает прирост качества без ручного перечисления эквивалентностей.

Пояснение:
- Это решает проблему “модель не знает ваших личных предпочтений”.
- Веса и reranker подстраиваются под реальные действия пользователя, а не под абстрактный датасет.

## Как интегрировать без ломки текущей архитектуры

1. Добавить новый модуль эмбеддингов:
- `app/embeddings.py`: единый интерфейс `embed_texts`, `embed_query`.

2. Добавить pipeline индекса:
- `app/build_job_index.py`: берет `jobdetails`, собирает тексты, считает `embedding_input_hash`, обновляет индекс только при изменениях.

3. Добавить модуль поиска:
- `app/search_jobs.py`: query/profile -> top-K вакансий (score + объяснимые причины).

4. Подключить в анализ:
- `app/analyze_jobs.py` получает shortlist и отправляет в LLM только top-K, сохраняя текущие правила версионирования `analysen`.

5. Сохранить существующие инварианты:
- неизменяемые имена основных коллекций (`stellenangebote`, `jobdetails`, `analysen`, `profiles`);
- идемпотентность и hash-based skip;
- секреты только через ENV;
- конфиги только из `conf/...`.

Пояснение:
- Подход “добавить слой, а не переписать систему” снижает риск регрессий.
- Текущие сильные механизмы проекта (hash/версии/история) сохраняются.

## Предлагаемые значения по умолчанию (старт)

- `K_RETRIEVE = 100` (первичный поиск)
- `K_RERANK = 50`
- `K_LLM = 20`
- `EMBEDDING_MODEL = intfloat/multilingual-e5-base`
- `SEARCH_MODE = hybrid`

Эти параметры стоит калибровать на реальных данных.

Пояснение:
- Значения выбраны как практичный компромисс между скоростью и качеством.
- На слабом CPU можно уменьшать `K_RERANK` и использовать `multilingual-e5-small`.

## Риски и как их контролировать

1. Drift качества поиска.
- Решение: метрики (MRR/NDCG/CTR) и регулярная калибровка.

Пояснение:
- Без измерений невозможно понять, улучшилась система или деградировала.

2. Рассинхрон Mongo и векторного индекса.
- Решение: `embedding_input_hash`, периодический reconcile job.

Пояснение:
- Если вакансия обновилась в Mongo, но не обновилась в индексе, выдача станет “устаревшей”.

3. Рост объема данных.
- Решение: ANN-индекс (Qdrant), контроль payload, пакетные обновления.

Пояснение:
- Это решает проблему деградации времени ответа при росте числа вакансий.

## Короткий итог

В проекте уже есть правильная база экономии LLM (идемпотентность и `input_hash` в анализе).  
Добавление локальных эмбеддингов и векторного presearch даст второй слой экономии: на LLM будут уходить только лучшие кандидаты, а не весь поток вакансий.

Идея в одной строке:
- сначала дешевый и быстрый смысловой отбор локально;
- потом дорогой и точный LLM-анализ только для shortlist.

## Практика при неполных данных и пограничных кейсах

Ниже описано, как система будет вести себя, если данные вакансии или профиля неполные.

### Случай 1: у вакансии есть только заголовок, описания нет

Пример:
- `Titel`: `DB Administrator`
- `stellenangebotsBeschreibung`: пусто

Как работает система:
1. В embedding-текст попадут доступные поля (заголовок, профессия, локация, занятость и т.д.).
2. Чанков описания не будет (или будет очень мало), поэтому `chunk_score` почти отсутствует.
3. Итоговый score формируется в основном за счет:
- совпадения названия профессии;
- совпадения коротких структурных полей.

Риски:
- меньше контекста для точного ранжирования;
- выше вероятность спорных совпадений между похожими ролями.

Что делаем, чтобы качество не падало:
1. Увеличиваем вес title/beruf-компоненты для документов с пустым описанием.
2. Добавляем признак `description_missing=true` в payload и понижаем confidence в финальном выводе.
3. Для top-кандидатов без описания можно запускать дополнительную проверку (reranker/LLM) только при необходимости.

### Случай 2: “чужая” роль с частичным совпадением по навыкам

Пример:
- Вакансия: `Web Designer`, в тексте есть фраза “неплохо знать Oracle/MySQL/Postgres/MsSQL”.
- Кандидат: позиционирует себя как `DB specialist`, навыки: Oracle/MySQL/Postgres/MsSQL.

Как работает система:
1. На уровне чанков/skills система найдет семантическое сходство по БД-терминам.
2. Но title/role-компонента (`Web Designer` vs `DB specialist`) даст отрицательный вклад в релевантность роли.
3. Итоговый score зависит от баланса весов:
- если роль/заголовок учтены правильно, вакансия не попадет в топ;
- если переоценить skills и недооценить роль, возможен ложный позитив.

Как правильно настраиваем, чтобы избежать ложных совпадений:
1. Вводим отдельный `role_score` (titel + hauptberuf + alternativBeruf).
2. Финальный score считаем как:
- `final = 0.40 * role_score + 0.35 * chunk_skill_score + 0.25 * profile_doc_score`
3. Добавляем штраф за конфликт ролей:
- если role-классы явно разные (design vs database), применяем penalty.
4. Опционально: rule-based gate:
- если `role_score < порога`, вакансия не попадает в top-N даже при хорошем skills score.

### Что будет, если профиль кандидата неполный

Пример:
- мало опыта/навыков в профиле, только общая формулировка.

Как работает система:
1. Снижается качество `profile_vector`, поэтому растет роль `query_vector`.
2. Результаты становятся более чувствительны к формулировке запроса.

Что делать:
1. Строить `query_expanded` (добавлять роль, локацию, язык, ключевые навыки).
2. Показывать пользователю подсказку “профиль неполный, добавьте навыки для точности”.
3. Использовать обязательные фильтры (локация/занятость/язык), чтобы снизить шум.

### Вывод по надежности в неполных данных

Система останется рабочей, если:
1. Разделять вклад роли и вклад навыков (не смешивать в один score без контроля).
2. Учитывать флаг полноты данных (`description_missing`, `profile_sparse`).
3. Применять пороги и штрафы для role-mismatch.

Тогда даже при “грязных” или коротких данных поиск останется практичным и управляемым.

## Быстрые правила (таблица решений)

| Ситуация | Что происходит без доп. правил | Что делаем в системе | Эффект |
|---|---|---|---|
| Нет `stellenangebotsBeschreibung`, но есть `titel/beruf` | Слабый контекст, риск неточного ранжирования | Повышаем вес `role_score`, ставим флаг `description_missing=true`, снижаем confidence | Вакансия не теряется, но помечается как менее надежная |
| Есть длинное описание с “водой” | Важные сигналы теряются в шуме | Чистка + chunking + hybrid retrieval | Лучше извлечение смысловых фрагментов |
| Роль вакансии и роль кандидата конфликтуют (`Web Designer` vs `DB specialist`) | Возможны ложные срабатывания по общим skills | Штраф за role-mismatch + порог на `role_score` | Меньше ложных попаданий |
| Профиль кандидата короткий/неполный | Ранжирование нестабильно | `profile_sparse=true`, усиливаем `query_score`, используем `query_expanded` | Выдача становится предсказуемее |
| Короткий пользовательский запрос | Мало контекста для семантики | Авторасширение запроса (роль, стек, локация, язык) | Выше recall и точность top-N |
| Много технических/системных полей в данных | “Засорение” embedding-текста | Жесткий exclude системных полей (`*_hash`, `*_dt`, `_id`, timestamps) | Стабильное качество embeddings |

## Минимальный чеклист перед запуском в прод

1. Включен fallback для `description_missing` и `profile_sparse`.
2. Включен `role_score` как отдельный компонент.
3. Есть penalty за `role-mismatch`.
4. Включен `query_expanded` для коротких запросов.
5. Системные поля исключены из embedding-текста.
6. Порог отбора в LLM задан (например, только top-20).
