# Локальный подбор вакансий: подробный план для новичка

## Зачем этот план

Цель: сделать локальную систему подбора вакансий высокого качества (DE/EN/RU), которая:
1. Работает на CPU.
2. Не требует облачного API для retrieval/rerank.
3. Дает качественные чанки для генерации `Anschreiben`.
4. Не пересчитывает эмбеддинги без реальных изменений данных.
5. Экономит вычисления за счет кэшей и инкрементальной обработки.

Ориентир по производительности:
- до `5100` вакансий;
- полный ночной пересчет в пределах `8-12` часов на `Intel i5-6300U`.

## Коротко: как будет устроен конвейер

1. Сбор актуальных вакансий (`stellenangebote + jobdetails`).
2. Слияние полей и очистка текста.
3. Сегментация предложений через spaCy (`de_dep_news_trf`, при необходимости RU-модель).
4. Semantic chunking (сохранение смысловых блоков: Aufgaben/Anforderungen/Benefits).
5. Embedding каждого чанка и summary вакансии.
6. Сохранение в Qdrant + payload-метаданные.
7. Поиск по запросу + профилю.
8. Rerank top-N.
9. Отбор лучших чанков для локальной LLM (написание Anschreiben).

## Компоненты и их роль

### 1) Qdrant (Vector DB)
- Что это: векторная БД для быстрого поиска похожих чанков.
- Задача: хранить векторы вакансий и метаданные (payload).
- Почему подходит: HNSW-индекс, быстрый поиск, фильтрация.

### 2) spaCy (`de_dep_news_trf`)
- Что это: NLP-пайплайн для точного разбиения текста.
- Задача: корректно выделить предложения в немецких текстах.
- Почему важно: вакансии часто содержат сокращения и смешанный стиль; грубый split снижает качество chunking.

### 3) Semantic chunking
- Что это: разбиение текста на смысловые куски, а не просто по символам.
- Задача: сохранить блоки требований/обязанностей целостными.
- Почему важно: для retrieval и для LLM лучше короткие, но смысловые фрагменты.

### 4) Embeddings (мультиязычные)
- Что это: перевод текста в вектор.
- Задача: искать похожие вакансии/чанки по смыслу.
- Базовая модель: `intfloat/multilingual-e5-large` (с fallback на `-base` при нехватке CPU/RAM).

### 5) Reranker
- Что это: модель второго этапа сортировки.
- Задача: переставить top-кандидатов точнее, чем обычный cosine.
- Модель: `BAAI/bge-reranker-v2-m3` (мультиязычный).

### 6) Локальная LLM (Anschreiben)
- Что это: генерация финального текста письма.
- Задача: использовать уже отобранные чанки, а не весь сырой документ.
- Модель-кандидат: `Qwen2.5 7B Instruct` (GGUF, Q4/Q5).

### 7) Нелокальные LLM через API (обязательно как опция)
- Что это: возможность использовать внешний API-провайдер вместо локальной модели.
- Провайдеры: `OpenAI API`, `Mistral API`.
- Задача: иметь единый сценарий работы, где можно переключать backend без переписывания пайплайна.

Почему это нужно:
1. Для сложных кейсов качество внешних моделей может быть выше.
2. Можно быстро сравнивать провайдеров A/B.
3. Есть fallback: если локальная модель недоступна, можно временно работать через API.

## Какие данные берем из вакансии

Основной принцип: сначала объединяем `meta + details`, потом строим текст.

Приоритеты полей:
1. `title`: `details.stellenangebotsTitel` -> fallback `stellenangebote.titel`
2. `role`: `details.hauptberuf` -> fallback `stellenangebote.beruf`
3. `alternatives`: `details.alternativBeruf*`
4. `description`: `details.stellenangebotsBeschreibung`
5. `location`: `arbeitsort.*` и `stellenlokationen.*`
6. `employment`: `arbeitszeit*`, `vertragsdauer`, `istGeringfuegigeBeschaeftigung`

Не берем в embedding:
- `_id`, `*_hash`, `*_dt`, timestamps, service-поля, run-метки.

## Что делать при неполных данных

### Нет описания (`description_missing`)
1. Поднимать вес role/title-компоненты.
2. Помечать документ флагом `description_missing=true`.
3. Снижать confidence и отправлять в LLM только при высоком суммарном score.

### Конфликт роли и навыков
Пример: `Web Designer` с упоминанием Oracle/MySQL.
1. Считать отдельный `role_score`.
2. Вводить штраф за role mismatch.
3. Использовать порог: низкий `role_score` не пускает вакансию в top.

## Как считаем score до LLM

Предложенная формула до генерации:

`pre_llm_score = 0.40*role_score + 0.30*chunk_score + 0.20*profile_score + 0.10*metadata_score - penalties`

Где:
- `role_score`: близость по title/beruf/hauptberuf.
- `chunk_score`: max/mean сходства query к лучшим чанкам.
- `profile_score`: близость profile к summary вакансии.
- `metadata_score`: совпадения по локации/занятости/языку.
- `penalties`: штрафы за role mismatch, missing critical fields.

После LLM:
- `llm_score` добавляется отдельно (не заменяет pre-LLM score).
- сохраняем оба значения для будущей калибровки.

## Как экономим вычисления (обязательно)

### 1) Инкрементальный embedding

Для вакансии храним:
- `embedding_input_hash`
- `embedding_model`
- `chunking_version`

Пересчитываем embedding только если изменилось хотя бы одно:
1. входной текст;
2. версия модели;
3. версия chunking-алгоритма.

### 2) Пропуск неизмененных вакансий

Если hash не изменился:
- не пересчитываем чанки;
- не обновляем векторный индекс;
- не гоняем rerank для этой вакансии в batch-задачах.

### 3) Кэш top-20 для пары (profile, query)

Ключ кэша:
- `selection_key = hash(profile_id + query_text_normalized + filters + retrieval_version)`

Если ключ уже есть:
- возвращаем готовый top-20;
- повторный retrieval/rerank не запускаем.

Инвалидация кэша:
1. изменилась вакансия из top-20 (существенно, по hash);
2. changed model/chunking version;
3. changed profile/query/filters.

## Как отдаем чанки в LLM для Anschreiben

1. Берем top-20 вакансий после rerank.
2. Для каждой берем top-2/3 чанка (самые релевантные).
3. Формируем компактный контекст:
- vacancy summary;
- релевантные требования;
- 1-2 блока обязанностей;
- ключевые ограничения (локация/формат).
4. Отсекаем маркетинговую “воду”, чтобы не раздувать контекст.

Результат:
- меньше токенов;
- меньше галлюцинаций;
- лучше фокус письма.

## Режимы LLM-входа (локально и через API)

Система должна поддерживать 2 режима входа:

1. `compact`:
- только релевантные фрагменты (top chunks),
- summary вакансии,
- профиль и запрос в сокращенном виде.

2. `full_context`:
- полный текст описания позиции,
- полный запрос пользователя,
- полный профиль кандидата,
- плюс релевантные фрагменты для акцентов.

Зачем два режима:
1. `compact` дешевле и быстрее.
2. `full_context` полезен для сложных случаев и более глубоких рекомендаций.

## Что именно должна генерировать LLM (универсальная задача)

Независимо от провайдера (`local/OpenAI/Mistral`) результат должен содержать:

1. `Einschreiben` (на целевом языке вакансии, обычно немецкий).
2. `match_assessment`:
- числовую оценку соответствия;
- краткое объяснение сильных/слабых сторон матча.
3. `candidate_recommendations`:
- что из опыта кандидата особенно релевантно именно для этой вакансии;
- чего может не хватать и как закрыть пробелы.
4. `interview_preparation`:
- какие темы с высокой вероятностью спросят;
- практические шаги подготовки.

Важно:
- рекомендации должны быть универсальными по доменам (IT, медицина, музыка и т.д.),
- но конкретизированными под пару `вакансия + профиль + запрос`.

## Унифицированный контракт результата LLM

Чтобы любой backend подключался одинаково, сохраняем единый JSON-формат:

1. `match_score` (0-100)
2. `decision` (fit/partial/not_fit)
3. `reasons` (ключевые аргументы)
4. `risks` (возможные слабые места)
5. `interview_topics` (что вероятно спросят)
6. `prep_plan` (как подготовиться за 1-2 недели)
7. `einschreiben` (готовый текст письма)
8. `model_provider` (`local` / `openai` / `mistral`)
9. `model_name`
10. `input_mode` (`compact` / `full_context`)

## Ночной режим (batch)

Ночью выполняем:
1. `build/refresh index` (инкрементально).
2. `recompute cached selections` для активных профилей/запросов (опционально).
3. отчет метрик:
- сколько вакансий changed/unchanged;
- сколько эмбеддингов пересчитано;
- время этапов.

## Что считаем успехом

1. Полный batch до 5100 вакансий укладывается в `8-12` часов.
2. Повторный запуск без изменений почти ничего не пересчитывает.
3. Top-20 стабильно релевантен по ручной проверке.
4. В LLM уходит компактный и осмысленный контекст.

## Отдельный механизм: анти-зацикливание выдачи (точные правила)

Проблема:
- если одни и те же вакансии стабильно лучшие и уже обработаны (`Anschreiben` создан для текущей версии),
  система может “крутиться” вокруг них и плохо продвигать новые позиции.

Цель:
- сохранить качество top-результатов;
- гарантировать появление новых кандидатов в каждой выдаче.

### Определения

1. `processed_same_version`:
- для вакансии уже есть `Anschreiben`;
- и версия/`input_hash` вакансии не изменились.

2. `base_top`:
- первые `20` вакансий после обычного scoring+rerank.

3. `fresh_pool`:
- вакансии из общего рейтинга, которых нет в `base_top`,
- и `processed_same_version=false`.

### Правила формирования финального списка

1. Берем `base_top = 20`.
2. Считаем `processed_in_top20` (сколько в `base_top` уже обработанных на той же версии).
3. Считаем число добавляемых новых:
- `extra_count = max(5, ceil(processed_in_top20 * 0.5))`
4. Добавляем из `fresh_pool` первые `extra_count` по рейтингу.
5. Ограничиваем общий размер:
- `final_size <= 50`
6. Если `fresh_pool` меньше `extra_count`, добавляем сколько есть.

Итог:
- `final_list = base_top + extra_new_candidates`
- размер обычно `25..50`.

### Правила приоритетов

1. Качество не ломаем:
- `base_top` всегда остается в начале (позиции 1..20 не переставляем этим модулем).
2. Новые позиции идут после base_top (21+).
3. Повторно обработанные без изменений не удаляем полностью, но не даем им монополизировать общий список.

### Псевдокод

```text
ranked = sort_by_score_desc(all_candidates)
base_top = ranked[:20]

processed_in_top20 = count(base_top where processed_same_version == true)
extra_count = max(5, ceil(processed_in_top20 * 0.5))

fresh_pool = ranked[20:] filtered by processed_same_version == false
extra = first N from fresh_pool where N = extra_count

final_list = base_top + extra
final_list = final_list[:50]
```

### Механизм v2 (следующий шаг): мягкий decay

Для уже обработанных без изменений вводится мягкий штраф:
1. `staleness_days = now - last_processed_at`
2. `decay_penalty = min(0.15, staleness_days * 0.005)`
3. `final_score = pre_llm_score - decay_penalty`

Правило:
- penalty применяется только если `processed_same_version=true`;
- при изменении версии penalty сбрасывается.

## Термины простыми словами

- `HNSW`: быстрый индекс ближайших соседей в векторном пространстве.
- `Embedding`: числовой вектор смысла текста.
- `Rerank`: второй этап точной перестановки top-N.
- `Payload`: метаданные в Qdrant (role, location, flags и т.д.).
- `Hash`: “отпечаток” входа для детекта изменений.
- `Chunk`: смысловой фрагмент исходного текста.
